# 回滚指南

> **证据状态**：已验证（现场 0.9.3 版本与五容器镜像，2026-11-24）｜代码推导（随包文档 `config/upgrade` 各节回退步骤、`manual-upgrade`、`backup-restore` 口径）｜待确认（本次升级是否产生数据库迁移、旧镜像归档与操作号是否留存）｜不适用（源码级回滚——无源码仓库）。
>
> 生产只读默认；回滚需审批。核心原则：**升级时留什么，回滚时用什么**；没留快照就不要贸然回滚。

## 1. 回滚前置（代码推导）

- 升级前必须记录：旧主镜像 / ONLYOFFICE 镜像归档与操作号、数据库迁移版本、活动任务、`installed-state.json` 的 `target`（composeFiles / env / project name）、共用镜像的侧车（docx-rewriter）。
- 0.9.3 升级路径中数据库沿用 `021_async_invocation_actor`，**无新迁移** → 主镜像/ONLYOFFICE 回退**不需要 SQLite 回退**（已验证于随包文档）。旧路径如 0.9.0→0.9.1 有 020→021 迁移，回退需停写并恢复停服快照（会舍弃快照后写入）。

## 2. 0.9.3 标准回滚（代码推导）

**两个服务各自单独回退**（主镜像与 ONLYOFFICE 互不牵连）：

```bash
# 用本次各自的旧镜像归档，配同一组 Compose / ENV
DOCKER_CONTEXT=default ai-agent-image rollback \
  --image <该服务旧镜像归档> \
  --project-name <项目名> --project-directory <实例根> \
  --compose-file <原顺序全部 compose> --env-file <原 env>
```

- 主镜像回退不影响 ONLYOFFICE，反之亦然；验收后分别清理本次传输介质。
- 只换回旧镜像**不能**撤销工具、共享软件、名称转换与数据库变更；相关变更需按对应迁移记录分别恢复。
- 0.7.2 之前单引擎/旧布局没有一键回滚，按 `manual-upgrade` 的新旧实例切换思路处理：新实例验收失败时切回旧实例端口，旧容器 `restart=no` 的处置反过来应用。

## 3. 数据库回滚（代码推导）

- 工具：`ai-agent-deploy restore <备份目录> --image-root <镜像目录> --config <file>`（**全量替换、不合并**）。
- 恢复演练在**无业务写入**的实例进行；恢复后核对项目与配置。
- 迁移库不能直接交回旧程序（如 018/019 迁移后的库不能给 0.8.1）；回退到旧库要先停写，再恢复停服快照 + 旧镜像。
- **不要用早期全量备份覆盖升级后的业务写入**；回退窗口结束后按空间规则清理临时快照。

## 4. 技能 / 工具回退（代码推导）

- 技能：删除本次安装的私有技能 `DELETE /api/skillshub/private/{skillName}`（实测可用）；公共技能治理只影响公共空间，不删用户私有副本。
- 工具 ZIP：按镜像内维护入口逐项 `remove` / `update <name> <zip>`；先镜像后 ZIP 的顺序在回退时同样要对齐，否则被覆盖。
- `webServer → publishUrl` 改名须与 ZIP/Agent 包一起回退；只回退镜像不能撤销改名。
- MCP：0.8.8 起为原生配置，旧 `mcp.zip` 不随包；回退旧版时按对应版本文档恢复配置。

## 5. 验收与风险

- 回滚后核对：四服务健康、`/api/health` 200、License、项目/模型/Workspace/私有文件保留、字体与工具正常、预览与 Office 编辑可用。
- 记录回滚原因、时间点、影响面与残余不确定性；经验收后更新本环境基线。
- 风险 R5：`/data` 已用 80%，回滚介质/快照需空间，先查余量。
- 风险 R2：无源码仓库，不涉及代码回滚；不要声称完成源码级回退。
